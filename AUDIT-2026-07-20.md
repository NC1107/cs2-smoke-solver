# Audit 2026-07-20: direction check + full-stack findings

Prompted by the question "am I detouring away from where the app should be?".
Produced by four parallel deep audits (solver/accuracy, performance, UX, reliability/ops) plus market deep-research, with every load-bearing claim re-verified against the code before inclusion.
Predecessor: AUDIT-2026-07-15.md (all 35 findings shipped); this audit does not repeat anything confirmed fixed.

## The direction verdict

Short version: the core thesis is intact and the recent work was mostly defensible, but the product answers a narrower question than the one that matters in a real round, and three structural drifts have accumulated.

### The two missing queries

Everything the tool can do today is one query shape: *point -> throws that land there*.
A real round needs two more shapes, and both concerns surfaced independently from the founder and from this audit's design-archaeology:

1. **Coverage, not landing distance ("does the smoke actually block the thing?").**
DESIGN.md's original problem statement is sightline denial: "given a target sightline, compute the full set of throws whose smoke blocks that sightline."
What shipped in the web product is a proxy: land within Nu of a clicked point.
A mid-doors smoke that lands 20u "precisely" but does not rise high enough to cap the lane is a useless smoke the tool currently calls perfect - the founder's own example.
The critical finding: **the real query is already built, tested, and CLI-exposed - the web UI just never surfaced it.**
`SightlineSpec(EyeA, EyeB)` + `LandingZoneSolver.Solve` are the stage-1 sightline->landing-zone solver, wired into the `lineups` and `solve` CLI commands (SolveCommand.cs:50, LineupsCommand.cs:70); `Occlusion.Test(smoke, eyeA, eyeB) -> SmokeBlocked(minCells)` already tests whether the settled `SmokeVolume` (SmokeFloodFill) actually caps a segment at eye height - exactly the mid-doors-too-low case.
So this is not a research project; it is a decomposition/wiring job: let the player define a sightline (two points, or a named gap), run the existing zone->lineup->occlusion pipeline behind `/api/lineup`, and badge each lineup "blocks / partial / does not block" from the real volume instead of a landing-distance guess.
That the built-and-tested version of the tool's stated core query was bypassed in the product surface is the single clearest piece of evidence for the "detour" worry.
It is also the deepest differentiation - no curated-lineup site can answer "does this actually block the lane".

2. **The forward query ("what can I smoke from HERE?") - solo executes.**
Executing B on dust2 alone, a player wants window AND doors smoked from the same approach; someone hitting from tunnels may not know a CT-spawn smoke is throwable from tunnels at all.
There is currently no way to generate targets from a throw position - only positions from a target.
Cheap implementation path: the warm cache already pre-solves every callout + pro hotspot map-wide; inverting that index (for each cached target solve, which lineups' feet fall within R of my position?) turns "click where you'll stand -> every meaningful smoke throwable from there" into a lookup, no new solving.
Grouped output = an execute package: N smokes, one position or short path, ordered.
Notably, this re-values two "detour" investments: the pro-demo hotspots define what "meaningful targets" means, and the cache warmer becomes the index that powers the feature.

### What this implies about identity

The founder's instinct - "maybe this is less a csnades.gg competitor and more a research/generation tool for in-depth lineup discovery" - matches what the code is actually good at: exhaustive physics-accurate search, a real in-game validation pipeline, and (with the two queries above) generation of execute plans no human has catalogued.
Curated-lineup sites compete on editorial polish; this tool's edge is computing what is not in anyone's catalogue - and the market research below confirms that edge is real but narrower than "we compute lineups and nobody else does": two competitors (Refrag/NADR, smokepractice.com) already compute lineups on demand.
What neither of them has is this project's in-game-validated error rate or a sightline-coverage query, which is what makes Tier 0a the load-bearing bet, not raw computation by itself.

### The three accumulated drifts

1. **Query-shape drift** - the two missing queries above; the deepest one, since the original design intent (sightline denial) was never surfaced in the product.

2. **Investment drifted from the accuracy core to presentation.**
Of the last ~80 commits, the largest single sink was the textured-3D pipeline (~10 commits), then pro-demo heatmaps (~5), while the repo's own named #1 accuracy lever - prop_static collision hulls, the root of the phantom-bounce sites - has zero code toward it and no backlog entry.
The UX audit judged the presentation features individually fine (all correctly gated/optional), so this is a prioritization drift, not wasted work.

3. **The trust-and-retention loop was never closed.**
The tool's differentiator is *provable* accuracy (a real validation pipeline with 9.8k in-game throws), but the Accuracy page reads as internal QA telemetry, is never linked from results, and the number players actually see (stability %) is unexplained and easily misread as a success probability.
Favorites do not survive a page reload, so the natural second visit ("the smoke I found yesterday") silently fails.
Retention infrastructure is the least-built part of the product.

## What the market research says

Deep-research pass across 20 sources (csnades.gg, csgonades.com, Yprac, Refrag/NADR, CS2UTIL, Smoke Baron, SCOPE.GG, smokepractice.com, Steam Workshop discussions, and community/press coverage), 19 claims confirmed by independent 3-vote adversarial verification (16 at 3-0, 1 at 2-0, all with primary-source quotes), 3 refuted, 3 timed out unverified on an API rate limit rather than being contradicted. Full detail in the research transcript; headline findings below.

**Two direct competitors already ship "compute a lineup on demand" - this is not an open niche.**
This is the single most important correction to make before finalizing direction. Refrag's NADR ships a "Grenade Finder": pick a landing point and a throw position, and the server calculates the angle (including stand/run/jump-throw) to hit it - a shipping, actively-marketed instance of exactly the core mechanic this tool leads with (wiki.refrag.gg/en/NADR, refrag.gg blog, 3-0 confirmed both). Separately, smokepractice.com is a closer match still: browser-based, no game client required, "real CS2 physics," users find and save their own lineups - directly the same pitch as this project, currently in beta and self-disclosing that "physics can be slightly off in places" (3-0 confirmed). Neither is validated in-game against real throws the way this project's pipeline is, and neither (from what was fetchable) does exhaustive map-wide sweep-and-rank or ships the sightline/occlusion query this audit's Tier 0 proposes - but the "compute, don't curate" wedge is occupied, not virgin territory. The differentiation has to be depth (physics validated against real in-game telemetry, exhaustive coverage per target, the sightline-coverage query) not the mere existence of computation.

**The dominant, most-adopted tools are curated libraries, not computed engines - and they win on scale and integration, not algorithm.**
Yprac Hub: 1,033,127 Steam Workshop subscribers, 5,233 ratings, 634,393 unique visitors, bundling 1,400+ hand-authored lineups in-game (3-0 confirmed) - the single largest number found anywhere in this research, and it is a curated library delivered where the player already is (the CS2 client), not a website. csnades.gg (1,416 video tutorials across 11 maps), csgonades.com (2,172 CS2 smokes, 40,789 registered users before its 2024-2025 acquisition), CS2UTIL, Smoke Baron (3,500+ video guides) are all curated catalogs, several explicitly hand-verified/re-checked by a human team after map patches rather than recomputed (CS2UTIL's "Report" + manual-review pipeline, 3-0 confirmed). One SEO-adjacent but directly on-point source argues the exhaustive-coverage model is actively counterproductive: "Most utility guides show you every possible lineup - and that is precisely the problem" (switchbladegaming.com, 2-0 confirmed), arguing for a small, repeatable, memorizable set over comprehensive options. That is a real objection this audit takes at face value: exhaustive results without a curation/ranking layer that surfaces the few worth memorizing is a liability, not a feature - which is exactly why the ranking-bug fix (item 1) and the "curated default view with a show-all escape hatch" UX finding (item 18, independently raised by the UX audit before this research ran) both matter more than raw exhaustiveness.

**In-game integration is a load-bearing adoption factor this project doesn't have.**
Yprac and the workshop practice maps live inside CS2 itself; a tab-switch to a browser is real friction the biggest incumbent doesn't impose. Yprac's own paywalling of most functionality visibly pushed players toward free alternatives (prosettings.net: "most of the functionality on those maps is now hidden behind a paywall, so that's not an option for most players," recommending HLTV's free community workshop maps instead, both 3-0 confirmed) - direct evidence that free + good-enough beats paywalled + comprehensive, which argues against ever gating this tool's core solve behind payment, and says nothing about needing in-client integration to compete on that axis specifically (staying free is the answer, not necessarily a plugin).

**Sustainability models cluster around three patterns, none of which map to a straightforward SaaS business.**
Donation-supported-and-free (csnades.gg's Patreon, explicit "only possible with support from you," 3-0 confirmed); freemium subscription (Yprac's paid "Premium Club," 3-0 confirmed); and absorption into an unrelated revenue platform (csgonades.com now 301-redirects into Clash.gg's skins-marketplace-and-casino platform, rebranded "Clash CS:GO and CS2 Nades," 3-0 confirmed - the flagship "exhaustive curated database" competitor no longer exists as an independent product). None of these validate a path to revenue for this project; they do validate that "stay free, take voluntary support" is a normal, sustainable posture for a tool this size, and that the alternative (get acquired into something unrelated) is a real fate for community nade sites that don't find their own footing.

**No direct evidence, for or against, on solo-execute demand specifically.** The three searches/claims closest to this question (SCOPE.GG's format, a reliability-threshold claim, and a "pro-derived must-know set" claim) all hit the API session limit before their votes completed and are unverified rather than refuted - genuinely absent evidence, not a negative signal. The switchbladegaming.com source that was verified argues for coordinated team executes over solo throws in general utility strategy, which is a different claim (team coordination vs. solo capability) and does not bear on whether players want a tool that shows everything smokeable from one stand spot.

**What this changes in the plan:** Tier 0a (sightline/coverage badging) is now the clearer of the two direction bets - it's the one no competitor was found to offer, and it directly answers the "does the smoke actually work" objection curated sites can't touch. Tier 0b (solo-execute packages) is unresearched territory, not de-risked by this pass - worth prototyping cheaply (it's mostly free, per the plan) but validate with a handful of real players before investing further. And the market data reinforces, rather than overrides, the trust/retention findings from the UX audit: with two competitors already computing lineups, this project's actual differentiators are (a) in-game-validated accuracy with a real published error rate, and (b) the sightline-coverage query - neither of which currently reaches a player looking at the site today.

## The plan

Ordered so each tier unblocks the next; effort in (S/M/L).
Tier 0 is the direction bet; the rest is the maintenance/quality floor that keeps the tool trustworthy while that bet is built.

### Tier 0 - the direction: close the two missing queries

These are what turn the tool from "a precise landing-spot finder" into "a lineup research + execute-generation engine" - the identity the founder is leaning toward and the one the code is actually built for.

0a. **Coverage badging via the existing sightline pipeline** (M - mostly wiring, the solver exists).
Expose `LandingZoneSolver` + `Occlusion.Test` behind the web path: player marks a sightline (or picks a named gap / "smoke this doorway"), and every returned lineup is badged blocks / partial / does-not-block from the real settled `SmokeVolume`, not landing distance.
Fixes the founder's mid-doors-too-low case directly and resurrects the tool's original stated purpose.
Intermediate step even without a full sightline UI: for an existing point target, run the occlusion test against the settled volume and show "smoke height / does it cap the lane" so a 20u-precise-but-too-low smoke stops being labelled perfect.

0b. **The forward query: "what can I smoke from here?" -> solo-execute packages** (M - index inversion, little new solving).
Invert the warm-cache index: for each map, over all pre-solved targets, bucket lineups by throw-spot; then a click on where you'll stand returns every meaningful smoke throwable from there (window, doors, CT, off-angles), grouped as an execute package (N smokes, one position or short path, ordered by throw sequence).
Surfaces the "you can throw a CT smoke from tuns and didn't know it" value the founder named.
Re-values two supposed detours: pro hotspots define "meaningful target", the cache warmer becomes the powering index.
Depends on the cache being trustworthy (Tier 1 item 2) since it reads cached solves directly.

### Fix now - live bugs found by this audit

1. **Ranking bug: stability is never an explicit sort key** (LineupApi.cs:519-526, S).
The chain is sky -> scatter -> exposed -> pins -> throw-type; stability only survives as an implicit stable-sort remainder BELOW throw-type, so a 45%-stability stand throw outranks a 100%-stability jump throw today.
Add an explicit `ThenByDescending(Stability)` (decide placement: above or below type - above matches the docstring's stated intent).
2. **Cache staleness is a failed mechanism, not a one-off** (LineupApi.cs:424, S interim / M durable).
`QueryVersion = 14` exists with a "bump when solver behavior changes" comment - and neither of today's two solver-behavior commits bumped it; only a manual purge prevented up to 30 days of stale results.
Durable fix: fold a hash of the built Solver/Sim assemblies into the cache key so staleness is impossible by construction; interim: CI check that fails when src/Solver|Sim changes without a QueryVersion bump.
3. **A cache-write failure silently discards a completed solve** (ServeCommand.cs:394-395, S).
The write sits outside any try/catch, after streaming has started: disk-full or a read-only remount kills the response with no log line and throws away 30s of compute.
Wrap it, log it, and still return the result; also make the write atomic (temp+rename, pattern already exists in ValidateCommand) and move PruneCache from startup-only to a timer.
4. **Favorites don't persist** (main.js:945, M).
In-memory flag only; a reload or even a re-search erases every star.
Key a localStorage map by the same physical-identity tuple permalinks already use; this is also the stated prerequisite for the backlog's rating system.
5. **Commit the irreplaceable data** (S).
86 of 161 validation reports and the newer per-map calibration files (markers-de_nuke.json, settings.json) are untracked on one dev machine; they cannot be regenerated without hours of live in-game throws.

### The accuracy core - the highest-leverage program

6. **Investigate the two phantom-bounce sites before building anything** (S).
Dump/visualize the collision triangles at dust2 [1428,1544] and inferno [692,-92,77] and diff against the real map.
Two candidate root causes exist (missing/over-represented prop_static hulls vs solid cloth/banner materials real grenades pass through - DESIGN.md's open per-triangle-surface-properties question); the evidence decides between an L-effort and an M-effort program, and these two sites alone carry ~44% of all confidently-wrong throws.
7. **Then execute the winning fix** (M-L).
If prop_static: a placement-lump reader + per-prop hull extraction into the .s2geo (add it to BACKLOG.md either way - the repo's best-evidenced accuracy lever currently has no backlog entry).
8. **Triage REST-MISMATCH separately** (M).
92 throws, median 63u but p90 1245u / max 2020u - the worst tail in the dataset, plausibly a settle/roll stop-rule edge case in GrenadeTrajectory's wall-slide branch rather than mesh error.
9. **Test the paths users actually run** (S-M).
The aimTarget re-aim path (every live query) has zero test coverage; there is no Cli.Tests project at all, which is exactly where the ranking bug lived.
Add aimTarget-parameterized siblings of the existing VerifyExact tests plus a pure-LINQ ranking-chain test.

### Performance - after the accuracy program is scoped

10. **Cache VoxelGrid per (map, attrs)** exactly like the colliders' Lazy pattern (TargetSolver.cs:75 vs MapRegistry.cs:31-43, S, zero risk) - the deferred half of tech-debt M1.
11. **Epsilon-gate the precision re-aim** (LineupSolver.cs:316-359, S).
The aimTarget branch always runs the full 5x5 exact-sim window; accept (0,0) when it already lands within ~16u of target and recover most of the +15% cold-solve regression.
Validate against data/validation before shipping - the epsilon is a real precision-vs-speed knob.
12. **Measure origin coarsening 24u -> 30/36/40u** (TargetSolver.cs:130, M).
Largest single lever (~50-60% of cold-solve time by geometry), real recall risk on narrow ledges; sweep step sizes through the validation harness and pick with evidence.
13. Concurrency DOP division under SolveGate (S, modest, do opportunistically).
